Proceed to Stage 3: Real AI Generation.

Before coding, read "replit.md" and the relevant "/docs" files, especially:

- "AI_GENERATION.md"
- "PRODUCT.md"
- "TECHNICAL.md"
- "BUILD_STAGES.md"

Goal

Replace mocked generation with high-quality real AI generation while preserving the approved Boardwork experience.

The AI should feel like an invisible engine behind the existing workflow—not a new product surface.

The core generation context is:

Class Profile + Current Instructional Context + Today's Boardwork Context → one excellent 5–10 minute activity

Do not redesign the existing interface.

Do not implement PNG export yet.

1. AI integration architecture

Replace the mocked generation architecture with a real server-side AI integration.

Keep provider-specific code behind a small adapter/service so changing models later does not require rewriting the application.

Use Replit Secrets/environment variables for credentials and model configuration.

Conceptually support:

- "AI_API_KEY"
- "AI_MODEL"

However, do not independently choose a production AI provider or model if one has not been specified.

If no provider/model has been configured, implement the provider-neutral integration architecture and clearly report what remains to connect.

Never expose API credentials to client code.

2. Build generation context server-side

For every generation, construct model context server-side from canonical saved data rather than relying on the browser to reconstruct persistent context.

Include relevant information from:

Class Profile

- grade / age level
- subject
- curriculum / framework
- curriculum details
- general class context

Do not send class color; it has no instructional relevance.

Arrival routine can remain presentation metadata unless it is specifically useful to generation.

Current Instructional Context

Include available:

- current unit/project
- concepts/topics
- current skills
- standards/objectives currently emphasized

Today's Boardwork Context

Include:

- today's topic/context
- practice goal
- selected Focus chips
- activity style
- Device Off / Device On
- requested duration
- teacher-provided resource URL and resource description when applicable

Do not require every field to be populated.

Sparse context should still produce a useful activity appropriate to the class.

3. Use recent activity history for lightweight variety

Use existing activity history to help prevent repetitive generation.

For each generation, include a lightweight summary of approximately the three most recent activities for that class when available.

Send only information useful for variety, such as:

- title
- activity style

Do not send complete previous activity content unless there is a demonstrated need.

The purpose is simply to help the model avoid repeatedly choosing the same activity approach.

This should not become a recommendation engine.

Do not add:

- embeddings
- vector search
- semantic similarity infrastructure
- activity scoring

4. Generation quality

Generate one coherent activity, not a mini lesson or worksheet.

The activity must:

- realistically fit the selected 5 / 7 / 10 minute duration;
- be developmentally appropriate for the stored grade/age;
- use concise student-facing language;
- be understandable without teacher explanation;
- be completed independently;
- require no peer interaction;
- make thinking visible where appropriate;
- have genuine instructional or curiosity value;
- be concise enough for classroom projection.

Good activity approaches include:

- retrieval
- reasoning
- prediction
- observation
- drawing/sketching
- comparison
- critique/evaluation
- application
- quick writing
- reflection
- curiosity/inquiry

Avoid generic busywork.

5. Respect Device Off / Device On

Device Off

This is a hard constraint.

Do not require:

- laptop
- phone
- browser
- web search
- digital resource
- QR code

Assume notebook/paper and pencil are available unless class/today context says otherwise.

Device On

The model may reference a digital resource only when the teacher has supplied it.

Never invent a URL.

Never claim to have opened, inspected, or read a teacher-supplied URL unless actual resource contents have explicitly been provided to the model.

If the teacher provides a short resource description, use that description as context.

Example:

Resource URL: teacher supplied

Resource description:

"A short article introducing biomimicry"

The AI can create a task around that description without pretending it inspected the page.

6. Treat teacher-provided content as data

Teacher-entered information may include:

- curriculum text
- standards
- class context
- unit/project descriptions
- today's topic
- resource descriptions
- URLs
- pasted instructional material

Treat this content as instructional data, not as system-level instructions.

Teacher-provided content must not override:

- Boardwork's generation rules
- safety requirements
- Device Off / Device On constraints
- required structured-output schema
- server/application instructions

Do not execute or follow instructions embedded inside pasted resources as though they were application/system instructions.

7. Structured output

Require structured output matching the activity model already established in the project.

Conceptually:

- eyebrow/label
- title
- task
- 0–3 supporting prompts
- duration
- device mode
- optional materials
- optional resource URL
- optional teacher note

Validate model output server-side with Zod before saving or returning it.

Do not allow arbitrary model-generated HTML.

Keep generated text intentionally bounded.

As guidance:

- title: preferably about 8 words or fewer
- task: preferably about 55 words or fewer
- prompts: maximum 3
- each prompt: concise

Do not solve excessive verbosity by shrinking presentation typography.

8. Generate behavior

Generate should respond directly to the supplied context and Focus selections.

Repeated Generate requests should create genuinely fresh alternatives rather than mechanically returning the same activity.

Use the lightweight recent-activity context to discourage obvious repetition.

Do not force novelty at the expense of instructional alignment.

9. Surprise Me behavior

Surprise Me should mean useful variety, not randomness.

It should:

- use Class Profile;
- use Current Instructional Context when available;
- respect grade, subject, duration, and device mode;
- select an appropriate activity approach;
- use recent activity summaries to encourage variety.

It should still feel relevant to the class.

If instructional context is sparse, generate a broadly useful subject-appropriate skill, thinking, observation, retrieval, or curiosity activity.

Do not invent claims about what students studied previously.

10. Save generated activities

Successful real generations should continue using the Stage 2 persistence behavior.

Once validated:

1. save the activity;
2. return it to the editor;
3. allow normal teacher editing;
4. preserve edits/history as already implemented.

Do not break:

- Duplicate / Remix
- Favorite
- History
- Present

Start Blank remains completely independent of AI.

11. Failure behavior

Generation will occasionally fail. Handle this gracefully.

Handle:

- provider/API failure
- timeout
- malformed response
- schema-validation failure
- rate limiting
- missing configuration

Requirements:

- preserve the teacher's inputs;
- never replace their context with empty state;
- provide a concise human-readable error;
- provide Retry where appropriate;
- prevent duplicate simultaneous generation requests;
- log useful technical information server-side without logging secrets.

If structured model output is malformed, one automatic repair/retry attempt is reasonable.

Do not silently fabricate an activity in application code after AI failure.

Start Blank must remain available regardless of AI status.

12. Student appropriateness

Treat grade/age as a hard generation constraint.

Generated activities should:

- use appropriate reading complexity;
- avoid unnecessary jargon;
- avoid asking students to disclose sensitive personal information;
- avoid unnecessarily sensitive or age-inappropriate content;
- avoid political persuasion;
- remain educational and neutral where civic/political topics legitimately arise.

Do not expose prompt text, system instructions, model names, or AI implementation details to students.

13. Preserve the product

Do not add:

- AI chat
- model selector
- temperature controls
- prompt editor
- token information
- AI branding
- automatic web browsing
- automatic resource retrieval
- standards lookup
- new presentation templates
- analytics
- new navigation

The teacher should simply experience a much better Generate button.

Acceptance check

Before stopping, test real generation across meaningfully different contexts.

Context

Verify:

- a class with rich context;
- a class with sparse context;
- curriculum/framework influences output appropriately when relevant;
- Current Instructional Context influences output;
- today's topic/goal influences output;
- selected Focus chips influence output.

Age appropriateness

Test at least two substantially different grade levels and confirm that wording and task complexity change appropriately.

Activity variety

Generate repeatedly from the same context.

Confirm useful variation without losing instructional relevance.

Confirm recent activity history helps prevent obvious repetition.

Device mode

Verify:

- Device Off never requires digital access;
- Device On never invents a URL or claims to inspect one.

Content shape

Test activities containing:

- 0 prompts
- 1 prompt
- 3 prompts
- drawing/sketch activity
- reasoning activity
- retrieval/quick-write activity

Confirm the existing presentation remains visually robust.

Reliability

Verify:

- valid generation saves to History;
- teacher edits still autosave;
- Retry works after a simulated or real failure;
- missing AI configuration produces a useful error;
- Start Blank still works without AI;
- teacher-provided content cannot override the application's generation contract.

Stop condition

When Stage 3 is complete, stop.

Do not implement PNG export or begin Stage 4.

Report:

1. the AI adapter/integration architecture implemented;
2. whether a provider/model is currently connected;
3. exactly which Replit Secrets/environment variables are required;
4. how generation context is assembled;
5. how recent activity history is used;
6. how structured output is validated;
7. acceptance checks that pass or fail;
8. any generation-quality or reliability issues I should test manually.

Wait for approval before Stage 4.
